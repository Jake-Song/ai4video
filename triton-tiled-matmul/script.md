# Triton의 tiled matmul: 출력 타일 하나를 따라가 보기

약 9분 분량의 대본입니다. 기본 행렬 곱과 입력 재사용부터 시작해, **화면 연출과 내레이션**을 함께 구성했습니다. 설명 범위는 Triton 공식 튜토리얼의 기본 matmul 커널입니다.

공통 화면 규칙: 왼쪽 상단의 행렬 곱은 모든 장면에서 `A(M × K) × B(K × N) = C(M × N)`으로 표시합니다. 어두운 남색 테마와 일반 글꼴을 사용합니다.

## 1. 00:00–01:45 | 타일링은 왜 필요할까?

**화면**

`A(M × K) × B(K × N) = C(M × N)`이 나타난다. 1-01은 다음 순서로 진행하며, 계산이 끝난 C의 칸은 색을 남겨 결과가 쌓이는 모습을 보여준다. 원소의 숫자 값이나 반복 횟수 표시는 넣지 않는다.

- A의 같은 행을 유지하고 B의 서로 다른 열을 차례로 계산한다. 결과가 C의 같은 행에서 옆 칸으로 들어가는 모습을 세 번 보여준다.
- 이어서 B의 같은 열을 고정하고 A의 서로 다른 행을 차례로 계산한다. 결과가 C의 같은 열에서 아래 칸으로 들어가는 모습을 세 번 보여준다.

이 두 동작만 진행하며, 행과 열을 동시에 바꿔 대각선으로 이동하는 연산은 넣지 않는다.

각 계산은 `행·열 선택 → 같은 K 위치를 따라 곱하고 더하기 → C의 해당 칸에 결과 넣기` 순서로 움직인다.

1-01 뒤에는 HBM 중복 전송의 비효율을 설명하는 흐름을 넣는다. 숫자 계산이나 횟수 표시는 사용하지 않는다. 기존 1-02~1-05의 번호와 수정 메모는 유지한다.

- 같은 A 행의 반복 전송: 출력 원소가 옆으로 이동할 때 B의 열만 바뀐다. A의 강조한 행은 그대로 두고, 같은 색의 입력 조각이 HBM에서 계산 영역으로 다시 이동하도록 그린다.
- 같은 B 열의 반복 전송: 출력 원소가 아래로 이동할 때 A의 행만 바뀐다. B의 강조한 열은 그대로 두고, 같은 입력 조각이 다시 전송되는 모습을 보여준다.
- 대역폭·대기 비용과 재사용: 반복 전송 경로를 강조한 뒤, 가져온 입력을 빠른 메모리에 남겨 여러 출력으로 나눠 쓰도록 바꾼다. 실제 HBM 접근은 캐시의 영향도 받는다고 표시한다.

이어서 큰 입력 행렬의 격자에서 작은 입력 타일을 강조한다. 강조한 타일의 복사본을 작은 격자로 옮기며 `Shared memory · Registers`를 표시한다. 같은 입력값에서 여러 출력 원소로 연결선을 그려 재사용을 보여준다. 마지막으로 C를 출력 타일들로 나눈다.

**내레이션**

“먼저 A의 행을 고정하고, B의 열만 차례로 바꿔 계산해 보겠습니다. 각 행과 열에서 같은 위치의 값끼리 곱하고 모두 더한 결과가, C의 같은 행에서 옆 칸으로 들어갑니다. 이번에는 B의 열을 고정하고, A의 행을 차례로 바꿔 보겠습니다. 같은 방식으로 곱하고 더하면, C의 같은 열에서 아래 칸들이 채워집니다.

출력마다 필요한 입력을 HBM에서 다시 가져오는 방식은 비효율적입니다. 옆 출력으로 이동할 때, B의 열은 바뀌어도 A의 행은 그대로 필요하죠. 같은 A의 행을 다시 읽는 만큼, 이미 가져왔던 데이터가 중복해서 전송됩니다.

아래에 있는 출력도 마찬가지입니다. 이번에는 A의 행이 바뀌고, B의 열이 그대로 필요합니다. 같은 B의 열을 HBM에서 매번 다시 가져오면, 여기에서도 중복 전송이 생깁니다.

이런 중복 전송은 메모리 대역폭을 차지하고, 입력이 도착하기를 기다리는 시간을 늘릴 수 있습니다. 그래서 한 번 가져온 데이터를 빠른 메모리에 두고 여러 출력의 계산에 재사용하는 겁니다. 실제 HBM 접근은 캐시의 영향도 받지만, 핵심은 같은 데이터를 다시 옮기는 일을 줄이는 데 있습니다.

큰 행렬은 GPU의 HBM에 저장됩니다. Shared memory와 Register는 HBM보다 빠르게 접근할 수 있지만, 용량이 작아 큰 행렬 전체를 담기는 어렵습니다.

그래서 필요한 입력을 작은 타일로 나눠 가져옵니다. 그리고 한 번 가져온 값을 여러 출력의 계산에 재사용해서, HBM에서 같은 데이터를 반복해서 읽는 양을 줄입니다.

Triton에서 행렬곱할 때 출력도 타일로 나누고, 각 타일을 계산하는 작업을 GPU에 분배합니다.

지금부터 출력 타일 하나가 완성되는 과정을 따라가 보겠습니다.”

**화면 자막**

`빠르지만 작은 메모리에 맞춰 나누기 → 입력 재사용 → HBM 접근 줄이기`

## 2. 01:45–02:25 | 타일의 크기를 정하는 세 가지 숫자

**화면**
왼쪽 상단 `A(M x K) x B(K x N) = C(M x N)`으로 표시

`A: M × K`, `B: K × N`, `C: M × N`을 표시한다.

C에 `BM × BN` 사각형을 그린다. A에는 `BM × BK`, B에는 `BK × BN` 영역을 강조한다.

**내레이션**

“A의 크기가 M 곱하기 K, B의 크기가 K 곱하기 N이라면, 결과 C의 크기는 M 곱하기 N입니다.

여기서 타일링을 결정하는 숫자는 세 가지입니다.

BM은 한 번에 계산할 출력의 행 개수, BN은 열 개수입니다.

그러면 출력 타일의 크기는 BM 곱하기 BN이 됩니다.

BK는 두 입력이 공유하는 K 방향을 한 번에 얼마나 처리할지 정합니다.

따라서 한 단계에서는 A의 BM 곱하기 BK 타일과, B의 BK 곱하기 BN 타일을 곱합니다.

이 곱의 결과는 출력 타일과 같은 BM 곱하기 BN 크기입니다.”

**화면 자막**

```text
BM = BLOCK_SIZE_M
BN = BLOCK_SIZE_N
BK = BLOCK_SIZE_K
```

## 3. 02:25–03:40 | CUDA와 Triton은 어떤 단위로 코드를 작성할까?

**화면**

화면을 좌우로 나누고, 양쪽에 같은 출력 행렬을 표시한다.

왼쪽 CUDA에서는 스레드를 작은 점으로, 스레드 블록을 점들을 묶는 테두리로 표현한다. `blockIdx`, `threadIdx`에서 행렬의 담당 위치로 화살표를 연결한다.

오른쪽 Triton에서는 여러 원소를 묶은 타일을 강조하고, `program_id → 담당 타일`을 표시한다. 이어서 타일이 컴파일러를 거쳐 여러 스레드에 배분되는 모습을 보여준다.

**내레이션**

“타일 계산을 보기 전에, CUDA와 Triton에서 코드를 작성하는 단위를 비교해 보겠습니다.

CUDA에서는 스레드와 스레드 블록을 명시적으로 다룹니다. 스레드 블록은 함께 협력할 수 있는 스레드들의 묶음입니다.

개발자는 블록과 스레드의 ID를 이용해, 각 스레드가 어떤 데이터를 읽고 어떤 결과를 계산할지 정합니다. 협력해서 타일을 계산한다면, 데이터를 나눠 읽는 방법과 필요한 동기화도 설계합니다.

Triton에서는 관점을 데이터 쪽으로 옮깁니다.

개발자는 ‘이 프로그램이 행렬의 이 타일을 읽고, 이 타일과 곱해서, 출력 타일을 만든다’고 표현합니다. 코드 안에서 다루는 값도 여러 원소로 구성된 블록 텐서입니다.

그 연산을 실제 GPU 스레드들에 어떻게 나눌지는 컴파일러가 처리합니다.

CUDA에서도 타일링을 구현할 수 있습니다. 두 방식의 차이는 타일을 쓰느냐보다, 개발자가 작업을 어떤 단위로 표현하고 스레드에 배분하느냐에 있습니다.

이제 Triton 프로그램 하나가 담당하는 출력 타일을 살펴보겠습니다.”

**화면 자막**

| 구분 | 개발자가 표현하는 작업 |
| --- | --- |
| CUDA | 스레드·블록의 ID를 이용해 담당 데이터와 연산을 배분 |
| Triton | 프로그램이 담당할 데이터 타일과 그 타일에 대한 연산을 표현 |

**제작 메모**

여기서 CUDA의 블록은 **스레드의 묶음**, Triton의 블록 텐서는 **데이터 원소의 묶음**이다. 화면에서 서로 다른 모양으로 구분한다. ‘CUDA는 스레드 하나당 원소 하나’, ‘Triton은 타일을 스레드 하나가 처리한다’는 고정된 대응으로 그리지 않는다.

[근거: Triton 공식 프로그래밍 모델 비교](https://triton-lang.org/main/programming-guide/chapter-1/introduction.html)

## 4. 03:40–04:25 | 프로그램 하나가 맡는 일

**화면**

설명용으로 A, B, C를 각각 `4 × 4`로 표시한다. C를 `2 × 2` 타일 네 개로 나누고 서로 다른 색을 입힌다.

각 타일에 `(0,0)`, `(0,1)`, `(1,0)`, `(1,1)`을 표시한다.

**내레이션**

“작은 예제로 보겠습니다. 두 입력은 모두 4 곱하기 4이고, 출력 타일은 2 곱하기 2로 정하겠습니다.

그러면 C에는 타일 네 개가 생깁니다.

기본 Triton matmul에서는 프로그램 인스턴스 하나가 출력 타일 하나를 맡습니다.

각 프로그램은 자신의 ID를 이용해, C의 어느 위치를 계산할지 정합니다.

예를 들어 왼쪽 위 타일을 맡은 프로그램은 A의 위쪽 두 행과 B의 왼쪽 두 열이 필요합니다.

다른 출력 타일들도 각자 계산할 수 있으므로, 이 작업들을 GPU에서 병렬로 실행할 수 있습니다.”

[근거: 공식 matmul 튜토리얼](https://triton-lang.org/main/getting-started/tutorials/03-matrix-multiplication.html)

**제작 메모**

`2 × 2`는 애니메이션용 크기다. 실제 커널에서 사용하는 타일 크기와 구분해 표시한다.

## 5. 04:25–05:35 | K 방향으로 움직이며 누적하기

**화면**

왼쪽 위 출력 타일을 확대한다. 옆에 `2 × 2` 크기의 누산기를 만들고 모든 값을 0으로 채운다.

첫 단계에서 A의 왼쪽 위 `2 × 2`, B의 왼쪽 위 `2 × 2`를 강조한다. 두 타일의 곱을 누산기에 더한다.

다음 단계에서는 A의 강조 영역을 오른쪽으로, B의 강조 영역을 아래로 이동한다. C의 강조 영역은 고정한다.

**내레이션**

“이제 왼쪽 위 출력 타일 하나에 집중해 보겠습니다.

먼저 중간 결과를 담을 누산기를 0으로 초기화합니다. 누산기의 크기도 출력 타일과 같은 2 곱하기 2입니다.

BK도 2라고 해보죠.

첫 단계에서는 K의 앞쪽 두 칸에 해당하는 A 타일과 B 타일을 가져옵니다. 두 타일을 행렬 곱한 뒤, 결과를 누산기에 더합니다.

하지만 출력은 아직 완성되지 않았습니다. K의 뒤쪽 두 칸이 남아 있죠.

A에서는 오른쪽 타일로 이동하고, B에서는 아래쪽 타일로 이동합니다. 이번 곱의 결과도 같은 누산기에 더합니다.

여기서 눈여겨볼 부분은 출력 위치입니다.

입력 타일은 K 방향으로 움직이지만, 우리가 완성하고 있는 출력 타일은 계속 같은 자리에 있습니다.

K 전체를 처리하면, 누산기에 이 출력 타일의 최종 값이 모입니다.”

**화면 수식**

$$
C_{0,0}
=
A_{0,0}B_{0,0}
+
A_{0,1}B_{1,0}
$$

**화면 자막**

`각 아래첨자는 원소가 아닌 타일의 위치`

## 6. 05:35–06:25 | 타일로 묶으면 무엇을 재사용할까?

**화면**

앞서 사용한 A 타일의 원소 하나를 강조한다. 그 값에서 출력 타일의 서로 다른 두 열로 선을 뻗는다.

B 타일의 원소 하나에서는 출력 타일의 서로 다른 두 행으로 선을 뻗는다.

**내레이션**

“이렇게 묶어서 계산하는 장점은 데이터 재사용입니다.

방금 예제에서 A 타일의 원소 하나는 출력 타일의 두 열을 계산하는 데 모두 쓰입니다.

B 타일의 원소 하나는 출력 타일의 두 행을 계산하는 데 모두 쓰이고요.

타일이 BM 곱하기 BN이라면, 한 K 단계에서 A의 각 값은 BN개 출력에, B의 각 값은 BM개 출력에 기여합니다.

같은 입력으로 여러 결과를 만드는 구조인 거죠.

타일링은 이런 재사용을 활용해, 데이터를 가져오는 비용에 비해 더 많은 연산을 하도록 만듭니다.

실제 메모리 접근 횟수는 캐시와 컴파일 결과에도 영향을 받지만, 이 재사용 구조가 성능을 높이는 출발점입니다.”

## 7. 06:25–07:15 | 이 과정이 Triton 코드에서는 어떻게 보일까?

**화면**

아래 코드를 한 줄씩 강조한다. 코드는 실행 가능한 전체 커널이 아닌 핵심 흐름으로 표시한다.

```python
acc = tl.zeros((BM, BN), dtype=tl.float32)

for ...:  # K 방향의 타일을 순회
    a = tl.load(...)
    b = tl.load(...)
    acc = tl.dot(a, b, acc)

tl.store(..., acc, ...)
```

**내레이션**

“지금 본 움직임을 코드에 연결해 보겠습니다.

`tl.load`는 계산에 필요한 입력 타일을 읽습니다. 실제 커널에서는 행과 열의 인덱스, 그리고 stride로 각 값의 메모리 주소를 계산합니다.

다음은 핵심인 `tl.dot`입니다.

여기서는 a와 b의 행렬 곱을 계산하고, 기존 acc에 더한 결과를 돌려줍니다.

a와 b가 타일이므로, 이 한 줄은 출력 타일 전체의 부분 결과를 계산하는 표현입니다.

예제처럼 FP32 누산기를 사용하면, 중간 합을 FP32로 유지할 수 있습니다.

K 방향의 반복이 끝난 뒤에는 필요한 출력 자료형으로 변환하고, `tl.store`로 결과를 저장합니다.”

[근거: `tl.dot` API](https://triton-lang.org/main/python-api/generated/triton.language.dot.html), [공식 커널](https://triton-lang.org/main/getting-started/tutorials/03-matrix-multiplication.html)

## 8. 07:15–08:05 | 타일 연산을 GPU 명령으로 바꾸기

**화면**

프로그램 하나의 타일이 여러 스레드에 나뉘는 개념도를 보여준다.

`타일 연산 → 컴파일러 → 스레드·메모리·GPU 명령` 순서로 연결한다.

**내레이션**

“앞에서 본 타일 단위의 연산은 실제 GPU에서 어떻게 실행될까요?

프로그램 하나의 타일 작업은 여러 스레드가 협력해서 처리합니다.

Triton에서는 개발자가 타일 단위의 연산을 표현하고, 컴파일러가 이를 GPU 스레드와 명령으로 배분합니다.

컴파일러는 공유 메모리 사용과 동기화, 그리고 지원되는 조건에서 Tensor Core를 활용하는 명령 선택도 처리합니다.

개발자에게 남아 있는 중요한 선택도 있습니다. 타일 크기와 프로그램당 워프 수, 파이프라인 단계 수 같은 설정입니다.

즉, 타일 단위로 알고리즘을 작성하되, 어떤 크기로 작업을 나눌지는 성능에 맞춰 조정하는 겁니다.”

## 9. 08:05–08:55 | 경계 처리와 마지막 장면

**화면**

행렬 가장자리에서 타일 일부가 바깥으로 나가는 모습을 보여준다. K 방향의 유효하지 않은 입력은 0으로 표시하고, 출력에서는 유효한 영역만 남긴다.

마지막에는 전체 C를 보여준다. 각 출력 타일 안에서 `읽기 → 곱하고 누적 → 저장`이 진행된다.

**내레이션**

“행렬 크기가 타일 크기로 딱 나누어떨어지지 않을 수도 있습니다.

K 방향의 마지막 타일에서는 범위를 벗어난 입력을 마스크로 걸러내고, 그 자리에 0을 사용합니다. 출력도 유효한 위치에만 저장합니다.

그리고 타일이 크다고 항상 빠른 것은 아닙니다.

큰 타일은 입력 재사용을 늘릴 수 있지만, 레지스터와 공유 메모리도 더 필요합니다. 그러면 동시에 실행할 수 있는 작업이 줄어들 수 있죠.

그래서 실제로는 여러 설정을 측정해 알맞은 조합을 찾습니다.

이제 전체 그림을 다시 보겠습니다.

프로그램들은 C의 서로 다른 타일을 맡습니다. 각 프로그램은 K 방향으로 입력 타일을 읽고, 행렬 곱의 결과를 누적합니다. K 전체를 처리하면 완성된 출력 타일을 저장합니다.

이 움직임을 기억하면, Triton matmul 코드의 타일 크기와 반복문이 각각 무엇을 뜻하는지 읽을 수 있습니다.”
